# nSelf Monitoring Stack

This directory contains the static configuration artifacts bundled with the nSelf CLI. `nself build` generates the runtime versions into your project directory. Do not hand-edit files that carry the `GENERATED BY nself build` header — they will be overwritten on the next build.

## Contents

```
monitoring/
├── alertmanager.yml               Alertmanager routing config (static reference)
├── rules/
│   └── otel-alerts.yml            Prometheus alert rules: OTEL Collector + Tempo
├── runbooks/
│   ├── otel-collector-down.md     Runbook for OtelCollectorDown / OtelSpanIngestDrop
│   └── tempo-down.md              Runbook for TempoDown / TempoScrapeErrors
└── grafana/
    └── dashboards/
        ├── tenant-trace-browser.json    Tenant-scoped trace browser (Tempo)
        └── error-rate-by-service.json  Error rate with Loki log drill-through
```

## Grafana Dashboards

Two dashboards ship with the CLI. Import both into your Grafana instance after deploying the monitoring stack via `nself start --monitoring`.

### Importing dashboards

**Via the Grafana UI:**

1. Open Grafana (default: `http://localhost:3000`).
2. Go to **Dashboards** → **Import**.
3. Click **Upload JSON file** and select the dashboard file.
4. On the import screen, map each datasource to your configured instance:
   - `Tempo` → your Tempo datasource
   - `Prometheus` → your Prometheus datasource
   - `Loki` → your Loki datasource
5. Click **Import**.

Repeat for both dashboard files.

**Via the Grafana HTTP API** (automation):

```bash
GRAFANA_URL="http://localhost:3000"
GRAFANA_TOKEN="your-service-account-token"

for dashboard in monitoring/grafana/dashboards/*.json; do
  curl -s -X POST "${GRAFANA_URL}/api/dashboards/import" \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer ${GRAFANA_TOKEN}" \
    -d "{\"dashboard\": $(cat "${dashboard}"), \"overwrite\": true, \"folderId\": 0}"
done
```

### Dashboard reference

#### nSelf — Tenant Trace Browser

**UID:** `nself-tenant-trace-browser`
**Datasource:** Tempo
**Refresh:** 30s

Browse distributed traces scoped to a single tenant. The `$tenant_id` dropdown pulls live values from Tempo resource labels.

| Panel | Description |
|---|---|
| Top 10 Slowest Spans | Table of the slowest root spans for the selected tenant. Click a Trace ID to open it in Tempo. |
| Request Duration Heatmap | Heatmap of span durations. Darker cells mean more requests at that latency bucket. |
| Error Rate | Time series of the error rate for the selected tenant. |

The tenant trace browser depends on services tagging spans with the `tenant.id` resource attribute. The nSelf plugin SDK sets this automatically. Verify with:

```bash
# Check that tenant spans are reaching Tempo
curl "http://localhost:3200/api/search?tags=tenant.id%3D<your-tenant-id>&limit=5"
```

#### nSelf — Error Rate by Service

**UID:** `nself-error-rate-by-service`
**Datasources:** Prometheus + Loki
**Refresh:** 30s

HTTP 5xx error rate per service with click-through from log entries to Tempo traces.

| Panel | Description |
|---|---|
| Overall Error Rate (5m) | Stat: current error rate across all services. |
| Services Reporting Errors | Stat: count of services with at least one 5xx in the last 5 minutes. |
| Total 5xx Errors | Stat: cumulative error count in the selected time range. |
| 5xx Error Rate by Service | Time series: per-service error rate. Filter by `$service` dropdown. |
| Error Logs → Tempo | Loki log panel. Each log line includes the `trace_id` field; click it to jump to the trace in Tempo. |
| Span Error Rate (OTEL) | Time series: error rate from OTEL spanmetrics (complements the HTTP metric panel). |

The Loki → Tempo click-through depends on `trace_id` being extracted as a Loki label. Configure this in `monitoring/loki.yaml`:

```yaml
# Excerpt from loki.yaml — pipeline_stages section
- json:
    expressions:
      trace_id: trace_id
      span_id: span_id
      level: level
- labels:
    trace_id:
    span_id:
    level:
```

The nSelf slog handler injects `trace_id` and `span_id` on every structured log record when an active OTEL span exists in the context. See `cli/internal/logging/logger.go`.

## Alert Rules

### OTEL alerts (`rules/otel-alerts.yml`)

| Alert | Severity | Condition | For |
|---|---|---|---|
| OtelCollectorDown | critical | `up{job="otelcol"} == 0` | 5m |
| TempoDown | critical | `up{job="tempo"} == 0` | 5m |
| OtelSpanIngestDrop | warning | span ingest rate drops >50% vs 30m baseline | 10m |
| TempoScrapeErrors | warning | `otelcol_exporter_send_failed_spans_total > 0` | 5m |

See `runbooks/otel-collector-down.md` and `runbooks/tempo-down.md` for response procedures.

## Alertmanager Routing

Critical alerts route to the `oncall-stub` receiver (email). Warnings are logged but generate no notification.

Configure the email destination via environment variable before running `nself build`:

```bash
export ALERTMANAGER_ONCALL_EMAIL="ops@your-domain.com"
nself build
```

The on-call stub is a placeholder. Replace it with a PagerDuty or Opsgenie integration in P98 when an on-call rotation is in place. See the `# P98:` comment in `alertmanager.yml`.

## Sampling Strategy

Tail sampling is configured in `otelcol-config.yaml` (generated by `nself build`):

| Policy | Rate | Target |
|---|---|---|
| Error spans | 100% | All spans with status=ERROR |
| High-volume endpoints | 1% | `/health`, `/metrics`, `/ping` |
| Default | 10% | All other spans |

Error traces always appear in Tempo. Health check traces appear rarely, keeping storage overhead low.
